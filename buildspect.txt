# Mission Operations Copilot — Frontend Build Specification

## 1. ROLE

You are building the **frontend only** for a Mission Operations Copilot application.

This is a hackathon/demo application for spacecraft mission anomaly investigation.

The frontend must feel like a professional **mission operations workstation**, not a generic chatbot.

The backend/RAG/AI/database will be implemented separately by another developer.

Do NOT implement the backend, database, embeddings, vector search, RAG pipeline, or LLM reasoning.

Your responsibility is:

- Frontend UI
- Navigation
- Dashboard
- Anomaly Center
- Investigation Workspace
- Evidence Explorer
- Telemetry visualizations
- Incident Timeline
- Audit Trail
- Loading/error/empty states
- Responsive layout
- API integration layer
- Mock data for development before backend integration

---

# 2. TECH STACK

Use:

- React
- TypeScript
- Vite
- Tailwind CSS
- Recharts
- Lucide React icons

Do not introduce unnecessary UI frameworks.

Use reusable React components.

Keep the code modular and easy for another developer to connect to a FastAPI backend.

---

# 3. VISUAL DIRECTION

Design language:

**Mission control / aerospace operations workstation**

The interface should feel:

- Professional
- Technical
- Dense but readable
- Data-oriented
- Trustworthy
- Modern
- Dark-mode first
- Suitable for a live judge/demo presentation

Avoid:

- Generic SaaS dashboards
- Excessive gradients
- Huge rounded cards
- Cartoonish graphics
- Excessive animations
- ChatGPT-like chat UI as the primary interface
- Decorative elements that don't communicate mission information

Use a dark interface with strong hierarchy.

Suggested visual hierarchy:

- Background: very dark navy/charcoal
- Panels: slightly lighter dark surfaces
- Borders: subtle
- Primary text: white/light gray
- Secondary text: muted gray
- Status colors:
  - Green = nominal
  - Yellow/amber = warning
  - Red = critical
  - Blue/cyan = informational/data
  - Purple = AI/inference where useful

Use status colors consistently.

# 23. TYPES

Create reusable TypeScript types.

At minimum:

```typescript
type Severity = "CRITICAL" | "WARNING" | "INFO";

type AnomalyStatus =
  | "OPEN"
  | "INVESTIGATING"
  | "RESOLVED";

interface Anomaly {
  id: string;
  title: string;
  subsystem: string;
  severity: Severity;
  status: AnomalyStatus;
  timestamp: string;
}

interface Evidence {
  id: string;
  source: string;
  subsystem: string;
  parameter: string;
  value: string;
  timestamp: string;
}

interface TelemetryPoint {
  timestamp: string;
  value: number;
}

interface TimelineEvent {
  timestamp: string;
  description: string;
  source?: string;
  severity?: Severity;
}

interface AuditEvent {
  timestamp: string;
  actor: "OPERATOR" | "SYSTEM" | "AI";
  description: string;
}
```

# 24. API SERVICE LAYER

Create:

```text
src/services/api.ts
```

Do not make API requests directly inside every component.

Create functions such as:

```typescript
getAnomalies()

getAnomaly(id)

getEvidence(id)

getTelemetry()

getTimeline(id)

getAuditTrail(id)

getInvestigation(id)

submitCopilotQuery(...)
```

Initially these can return mock data.

Later replace the implementation with FastAPI requests.

Expected backend endpoints are approximately:

```text
GET  /api/anomalies
GET  /api/anomalies/{id}
GET  /api/evidence/{id}
GET  /api/telemetry
POST /api/investigations
POST /api/copilot/query
GET  /api/timeline/{incident_id}
GET  /api/audit/{incident_id}
```

Keep the frontend architecture independent of whether data comes from mock data or the real API.
